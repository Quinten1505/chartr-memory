# Choose the memory runtime and agent tool boundary

## Question

Who owns the memory service connecting to the operator's existing Windows-hosted SurrealDB instance, and how do Codex, Claude Code, and Grok on macOS/Linux discover and authenticate to the typed memory tools? Honor the existing-history compatibility contract and resolved provider/rollout contract. Choose where the memory service runs and whether the cross-machine boundary exposes that service, uses a tunnel, or connects to the database directly; specify endpoint discovery, authenticated transport, credential ownership, and connection-failure behavior. The currently verified database listener is Windows loopback, not an established remotely reachable endpoint. Decide service lifetime across Chartr restarts and durable Herdr sessions, configuration ownership, startup/bootstrap delivery, attribution of writes, and behavior when the existing database or embedder is unavailable. Do not substitute a newly provisioned unrelated database. Define the full tool schemas and errors, reconciling the draft's 'five tools' with its seven listed tools and missing confirmation fields. Compare the existing native plugin/service seam with an independent memory-service sidecar; choose a boundary, not an implementation task list.

Options for discussion (not decisions):

- Independent local memory service used by Chartr and provider MCP clients
- Chartr-managed sidecar with explicit behavior when the desktop closes
- Native Chartr service exposing a narrow provider-facing bridge

## Done when

A selected process/ownership model, provider wiring contract, typed tool surface, configuration contract, and failure semantics are detailed enough to implement without inventing host capabilities.

## Answer

Confirmed by the operator on 2026-09-26. [Discussion history](../assets/runtime-tool-boundary-discussion.md) records the choices and the revision from native-ID inference to scoped session grants. This Answer is the canonical contract.

## Process and network boundary

- Run one independent memory service on the existing Windows database host. It connects to the existing Windows-loopback SurrealDB instance in namespace harness, database memory. The service, not Chartr or provider processes, owns the database credential, schema compatibility checks, legacy-history adapter, and binding enforcement. It starts independently of Chartr and remains available while Chartr closes.
- Expose only the memory service to the current private routed network using authenticated HTTPS. Do not expose SurrealDB or rely on an unverified remotely reachable database listener. Chartr stores a service endpoint name and trust configuration per installation; changing that endpoint can later move the service to a dedicated host without changing memory-project or conversation identity. Tailscale routing and a dedicated host are later deployment work, not a prerequisite for this release. If the service moves while the database remains on Windows, its database connection must be separately secured and retested.
- Keep a versioned service protocol and health endpoint. A host move changes deployment configuration, not card IDs, scope rules, client installation identities, or provider tool schemas.
- Keep the memory-service core host-independent and its database endpoint configurable. The first deployment uses a Windows service wrapper; a future dedicated host must not require a semantic-data migration merely because the process moved.
- Chartr manages its own Codex, Claude Code, and Grok Build MCP entries at user scope, preserves unrelated entries, detects project overrides and drift, and reports per-provider availability. It does not assume one shared .mcp.json is forwarded to all providers. Required provider releases and behavior must be verified on macOS and Linux.

The transport choice is grounded in the providers' official [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli), [Claude Code MCP](https://code.claude.com/docs/en/mcp), and [Grok Build MCP](https://docs.x.ai/build/features/mcp-servers) documentation. Each documents local stdio MCP; this does not yet prove Chartr's per-session launch propagation on the selected binary releases.

## Session authority and lifetime

- Chartr registers its operator-selected memory binding for a new internal conversation before provider launch: client installation, provider, conversation, work/personal boundary, optional memory project, applicable repository/worktree, and private-access flag. A change of project or boundary starts a fresh conversation. The service stores the binding and issues an opaque, scoped session grant. Provider-native session IDs are installation-qualified evidence aliases attached when verified; they never authorize or select a binding.
- Each provider loads a Chartr-managed local stdio MCP bridge. Chartr supplies only that conversation's opaque grant through a launch-time mechanism that does not put it in shell history or a repository file. The bridge authenticates the Windows service over HTTPS, refreshes short-lived scoped access using a protected client-installation credential and the registered conversation grant, and remains alive with the provider when the Chartr UI exits. The installation credential is held in an OS credential store or an equivalent owner-only secure store supported on Linux; it is not written into provider MCP configuration, a project file, or model-visible tool output. The service checks both installation and registered conversation before renewal. Revocation or explicit session end stops renewal and future tool calls; merely closing Chartr does not.
- The current launch path can deliver initial input and agent-profile environment, but does not prove secure per-session environment delivery to every provider MCP child. Implement a trusted launch/broker seam and verify it for each required provider and OS. Do not treat an agent-supplied session ID, cwd, project parameter, or direct card ID as authority. The agent can choose narrower scope only within its registered binding.
- Chartr supplies a short instruction to call memory_bootstrap at the start of project work and verifies the configured MCP bridge. It does not preload memory text into the prompt. A newly started or explicitly resumed session is the access guarantee; already-running sessions need not gain tools without restart/resume. A Free session can bootstrap eligible operator-wide preferences within its chosen boundary but receives no project records.
- Every new write gets a service-assigned source-run identity linked to the registered conversation, client installation, provider, binding, method, and time. Native session/turn/evidence locators may be attached later without changing the source-run ID. An absent or ambiguous transcript pointer is labeled, never invented. Automatic capture uses an internal authenticated ingestion path owned by the same service; [Define automatic capture and extraction semantics](../tickets/07-automatic-capture-contract.md) chooses its trigger, cursor, replay, and extraction policy.

## Tool envelope and access rules

The public agent surface has **seven** MCP tools; the draft's â€œfive toolsâ€ count is corrected. Every call is bound by its bridge connection, not by an input project string. Read filters compose work/personal, private, project or eligible operator preference, repository, worktree, session, lifecycle, and legacy mapping checks. Direct lookup, graph expansion, evidence, and history follow the same checks. Unknown or unauthorized IDs return the same not_found result.

Shared write fields: idempotency_key is required for every mutation; expected_revision is required for an amendment, status change, or semantic replacement. The service derives actor and source-run attribution. scope_level is one of project, repository, worktree, conversation, or operator_preference. The first four resolve only to identities in the registered binding; project is unavailable to a Free session. operator_preference is allowed only for a preference proposal in the binding's work/personal boundary. A write may request private visibility only when that permission is in the binding. Raw scope arrays, database IDs, confirmation booleans, and agent-selected provider/session attribution are absent from agent input.

Schema vocabulary: type is one of decision, constraint, convention, lesson, incident, skill, preference, fact, concept, thought, schema_proposal, component, interface, episode, artifact, person, vendor, tool, project, repo, or symbol. Graph verbs and their typed endpoint restrictions are the closed list in the [ontology draft](../../../../surrealdb-agent-memory-ontology-design.md#8-edge-types), with the supersession cardinality and authority corrections from [Set the knowledge lifecycle and authority rules](../tickets/05-knowledge-lifecycle-contract.md). Project and repository identity rows are created through trusted registration, not by agent memory_remember or memory_reclassify. Inputs containing unknown enum members or unvalidated type-specific fields fail. IDs returned by the service are opaque, scoped public handles; clients do not construct SurrealDB record IDs.

Wire types make the table implementable without adding authority-bearing parameters later:

- All IDs and idempotency keys are nonempty strings; IDs are server-issued handles, while a new slug is a validated writer-controlled string. Revisions are nonnegative integers. Unknown fields fail validation. Optional booleans default false unless stated otherwise. A requested limit or max_tokens must be positive and no greater than the server cap set by the retrieval contract; excess is invalid_input rather than silent truncation.
- The read view is current (default), proposals, or history. The optional read narrowing object contains only repository_id and worktree_id, each of which must equal an identity in the registered binding. It cannot select a new project or boundary. Each result labels its status and whether evidence is readable, unavailable, or ambiguous.
- memory_bootstrap accepts {max_tokens?: integer, include_global_preferences?: boolean = true, include_inbox?: boolean = false}; it returns {binding_summary, groups, tokens_est, health}. memory_recall accepts {query: nonempty string, types?: closed type[], limit?: positive integer, max_tokens?: positive integer, view?: read view, include_global_preferences?: boolean, narrow_to?: read narrowing}; it returns {cards, tokens_est, health}. memory_get accepts {id: card ID, view?: read view}; it returns {card}.
- memory_remember create accepts {mode: create, type: agent-writable closed type, slug, title: nonempty string, body?: string, scope_level, private?: boolean, tags?: string[], extra?: type-validated object, links?: allowed link[], idempotency_key}. Amend accepts {mode: amend, id: card ID, expected_revision, patch: nonempty object of title/body/tags/validated extra, reason: nonempty string, idempotency_key}. It returns {card}; neither mode accepts a status, raw scope token, author, source_run, or confirm value.
- memory_link create accepts {mode: create, from_id: card ID, verb: closed edge verb, to_id: card ID, meta?: verb-validated object, idempotency_key}. Amend accepts {mode: amend, edge_id: server-issued ID, expected_revision, meta: verb-validated object, reason: nonempty string, idempotency_key}. It returns {edge_id, revision}. A link never widens either endpoint's visibility.
- memory_status accepts {id: card ID, target_status: legal type status, expected_revision, idempotency_key, reason?: string, evidence_ids?: authorized evidence ID[], successor_id?: card ID}; it returns {card}. A transition requiring evidence rejects an empty or unverifiable evidence_ids list. An agent cannot use this schema to request operator-only transitions.
- memory_reclassify accepts {from_id: thought ID, to_type: agent-writable closed type, to_slug, expected_revision, idempotency_key, title?: string, body?: string, scope_level?: permitted no-wider scope, extra?: type-validated object, links?: allowed link[]}; it returns {thought, card}. The target's default status is server-selected.

Responses use one versioned structured envelope: success has request_id, card or cards, revision where applicable, and optional warnings; failure has request_id and error {code, message, retryable, optional retry_after}. Cards carry stable scoped identity, type, status, revision, source attribution, available evidence pointers, and explicit unavailable-source markers. The retrieval ticket owns result ordering and presentation budgets. No raw SurrealDB errors or restricted record metadata are returned.

Errors include unauthenticated, session_revoked, binding_missing, backend_unavailable, schema_incompatible, invalid_input, unknown_type, operator_only_type, unknown_verb, invalid_scope, not_found, conflict, revision_conflict, idempotency_conflict, invalid_transition, operator_confirmation_required, evidence_required, and source_unavailable. Unauthorized record IDs use not_found; a wrong binding is never repaired from agent arguments. Transport failures are normalized by the local bridge to a retryable connection_unavailable error when it can answer; Chartr separately reports connection state.

## Operator control and failure behavior

- A separate authenticated Chartr control API owns installation pairing/revocation, binding registration, service health, legacy mapping/review, operator confirmation/activation, publication and withdrawal, and any private-access change. It enforces the lifecycle's expected-revision and audit rules; a provider approval prompt is not proof of operator authority. The minimal UI interaction belongs to [Find the minimal operator memory controls](../tickets/09-operator-memory-controls.md).
- If the service or database is unavailable, Chartr still launches the coding terminal and visibly reports memory unavailable. Reads and writes fail explicitly; no silent local write queue or fabricated successful result is allowed. Recovery is by retry in the same valid registered session or by an explicit resume/new session if the bridge or grant could not be established at launch. If the service is down before grant registration, the terminal launches without memory and must resume/relaunch after recovery to acquire it.
- If the embedder fails, typed writes continue without embeddings and scoped lexical retrieval continues with a visible degraded status. The retrieval ticket defines lexical ranking, later embedding backfill, and quality thresholds. A healthy database with a failing harness-memory adapter must be diagnosed as an adapter failure, not reported as absent history.
- The service reads eligible old cards through the agreed adapter in the same database. Unmapped tags, ambiguous two-project cards, unreviewed post-cutover writes, and changed fingerprints stay outside ordinary access. Existing client coexistence and old-row meanings remain intact. Startup distinguishes transport, authentication, database, schema compatibility, legacy mapping, and embedder health; a schema incompatibility blocks memory writes and rollout without blocking the coding terminal.

## Proof required before implementation handoff

Verify a named release of all three providers on both macOS and Linux: managed stdio bridge discovery, launch-time scoped grant delivery, bootstrap, fresh/resumed sessions, project config shadowing, client restart, Chartr closure with a live Herdr terminal, grant renewal/revocation, and all six directed cross-provider continuity pairings. Test wrong-scope direct lookup, graph/evidence traversal, Free sessions, private access, and operator-wide preference proposals. Test network interruption, service/database failure, embedder failure, and recovery without a duplicate or lost successful write. Test the exact existing SurrealDB/T3 client snapshot and its additive schema startup before rollout. The operational ticket owns the final matrix and recovery thresholds.
