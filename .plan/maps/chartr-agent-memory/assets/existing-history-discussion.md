2. After mapping, trust the existing accepted and active statuses for the cutover history. Preserve their original status meanings and exclude proposals from ordinary retrieval.
3. Preserve existing records and current client meanings. Read them through a compatibility adapter, with only additive, versioned storage changes for the new identity and provenance contract.
4. Review each of the four cards carrying two project tags. Choose a home project and publish an operator-approved snapshot to another project where appropriate; do not alter the original card or tags.
5. Show eligible legacy cards with their known agent author and an explicit missing-source-details marker when source-run or evidence links are absent.
6. Grandfather the 54 cards present at cutover, rather than automatically trusting accepted/active records the current T3 client writes later. Later writes require review.
7. When Chartr corrects a legacy card, use a guarded compatible status transition where possible so current T3 clients stop seeing the old card as live. Do not silently leave stale authority in the old client.

The operator confirmed the summary of choices 1–5, then confirmed these safeguards: grandfather the cutover set by original record ID plus content/status/scope fingerprint; require review of later legacy writes or semantic edits; use a guarded, atomic legacy status transition only when the type supports a semantically correct terminal state; otherwise wait for a compatible migration before claiming cross-client correction.
